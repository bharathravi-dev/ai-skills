## 1. Learning objectives

1. **Write** an `inputSchema` that rejects the argument mistakes models actually make, and **measure** what each
   layer of validation catches.
2. **Choose** the right schema for a tool that takes no parameters, and explain the risk of the permissive one.
3. **Use** `outputSchema` and `structuredContent` to turn silent output drift into a detectable failure, on both
   the server and the client side.
4. **Apply** MCP's JSON Schema rules: 2020-12 as the default dialect, no automatic dereferencing of network
   `$ref`s, and bounded validation work for composition keywords.

---

## 2. Vocabulary

| Term | Definition |
|---|---|
| **JSON Schema** | A JSON vocabulary for describing and validating JSON values. MCP defaults to draft **2020-12**. |
| **`inputSchema`** | Required on every tool: the schema its `arguments` object must satisfy. Root `type` must be `"object"`. |
| **`outputSchema`** | Optional: the schema a tool's `structuredContent` must satisfy. |
| **`structuredContent`** | A tool result's machine-readable value (any JSON value, since 2026-07-28), as opposed to `content` blocks. |
| **Output drift** | A server's actual output diverging from what clients expect, typically after a release. |
| **`$ref`** | A reference to another schema, local (`#/$defs/money`) or by URI. |
| **Composition keywords** | `anyOf`, `oneOf`, `allOf`, `not`, `if`/`then`/`else` — combine subschemas. |

---

## 3. Plain-language explanation

### 3.1 Two contracts per tool

A tool definition makes two promises. The **input schema** says "this is what you must send me." The optional
**output schema** says "this is the shape of what I will send back." MCP borrows the vocabulary for both from
**JSON Schema**, which M5-L06 used to constrain model output. This lesson is about using those two contracts
seriously — as validation, not just documentation.

### 3.2 Models make predictable argument mistakes

Language models produce arguments as text, and their mistakes are not random: numbers arrive as strings (`"40.00"`),
enum values arrive in the wrong case (`"Late"`), field names arrive in the wrong convention (`orderId`), and
occasionally a plausible extra field appears (`"override_limit": true`). §7.1 ran 12 such payloads against a
refund tool's schema. Checking only that required keys existed caught **2**; adding basic type checks caught
**6**; the full schema — patterns, ranges, enums and `additionalProperties: false` — caught **all 12**.

### 3.3 A server's output can change under you

Output schemas matter most when nothing crashes. §7.3 simulated a server release that renamed `status` to
`state`. A client reading `result["status"]` got `None`, decided 50 out of 50 delivered orders were not eligible
for refunds, and raised no error at all. The same client validating results against `outputSchema` flagged
50 out of 50 results as off-schema — the difference between a silent wrong decision and a loud, attributable failure.

### 3.4 Schemas are input too

A schema arrives from a server, and a server may be careless or hostile. MCP therefore adds rules about schemas
themselves: don't follow `$ref`s to network addresses (§7.5 shows one pointing at a cloud metadata endpoint), and
bound how much work validation may do (§7.6 shows a 1.6 kB schema that demands 32,762 evaluations).

## 4. Analogy

**A customs declaration form and a packing list.** The declaration form (input schema) has boxes with rules:
"value in euros, digits only", "country from this list", "sign here". A clerk who only checks that every box is
*filled* waves through "forty-ish" in the value box; a clerk who checks the rules does not. The packing list
(output schema) is the sender's promise of what is in the box. If the supplier quietly starts labelling
"shoes" as "footwear", a warehouse that checks the list against its expected categories notices the first
shipment; one that doesn't files every pair under "unknown" for months.

### Where the analogy breaks

- **Customs forms are designed by the recipient; MCP schemas come from the sender.** A server writes the
  `inputSchema` that clients validate against. A malicious server can therefore hand a client a schema designed
  to hurt the validator (§7.5, §7.6) — something no customs form does.
- **A form is filled by a person who read the instructions; arguments are generated by a model that read the
  schema as text.** The schema is simultaneously a validator and a prompt, and its descriptions affect what
  the model produces (M9-L15).

## 5. Detailed technical explanation

### 5.1 What MCP requires of schemas

`[VERIFIED 2026-09-15 — MCP 2026-07-28, Base Protocol §JSON Schema Usage and Server Features §Tools]`

| Rule | Detail |
|---|---|
| Default dialect | JSON Schema **2020-12** when no `$schema` is present; other dialects MAY be declared via `$schema` |
| `inputSchema` | MUST be a valid JSON Schema object (not `null`); root `type: "object"`; since 2026-07-28 **any** 2020-12 keyword may appear |
| No-parameter tools | `{"type":"object","additionalProperties":false}` is **recommended**; `{"type":"object"}` accepts any object |
| `outputSchema` | Optional; if present, servers **MUST** return conforming `structuredContent`; clients **SHOULD** validate |
| `structuredContent` | Any JSON value since 2026-07-28; a tool returning it SHOULD also return the serialized JSON as a `TextContent` block |
| `$ref` | Implementations **MUST NOT** automatically dereference network URIs; opt-in fetching must be off by default |
| Composition | Implementations SHOULD bound depth, subschema count or validation time |

Two terms are easy to confuse: `structuredContent` is **server-produced result data**. It is unrelated to a model
provider's "structured outputs" feature, which constrains what a model generates.

### 5.2 What each layer of input validation catches

`[REAL, measured]` §7.1 validated 14 payloads (2 correct, 12 flawed) against this schema:

```json
{"type":"object",
 "properties":{
   "order_id":{"type":"string","pattern":"^O-[0-9]{4}$"},
   "amount":{"type":"number","minimum":0.01,"maximum":500},
   "reason":{"type":"string","enum":["damaged","late","wrong_item","other"]},
   "notify_customer":{"type":"boolean"}},
 "required":["order_id","amount","reason"],
 "additionalProperties":false}
```

| Validation depth | Caught | What slipped through |
|---|---|---|
| Required keys present | 2/12 | Everything except `missing reason` and `orderId` |
| + JSON types | 6/12 | Negative and huge amounts, wrong enum case, invented enum value, bad id format, extra field |
| Full schema | **12/12** | — |

Three observations:

- **Most dangerous mistakes are type-correct.** `-40`, `40000`, `"goodwill"` and `"override_limit": true` all
  have perfectly valid JSON types. Only ranges, enums and `additionalProperties: false` stop them.
- **Coercion is a decision, not a default.** Accepting `"40.00"` as `40.0` is convenient; accepting `"$40"` is
  not. If you coerce, do it explicitly, document it, and re-validate afterwards (M5-L07).
- **Validation belongs on both sides.** A host can validate before sending, saving a round trip and letting the
  model retry with a precise message; the server MUST validate regardless, because clients can be buggy or
  malicious (M9-L13).

### 5.3 The no-parameter tool

`[REAL, measured]` §7.2 sent five argument objects to `get_current_time`: `{}` plus four invented flags
(`force`, `all_regions`, `confirm`, `dry_run`). `{"type":"object"}` accepted **5/5**;
`{"type":"object","additionalProperties":false}` accepted **1/5**.

The permissive schema is legal, and harmless *if* the handler ignores everything it receives. The risk is
future-facing: once a handler reads a keyword argument — added for an internal caller, a test, or a debug flag —
a model that invents that name can switch the behaviour on. The strict schema closes that door on day one.

### 5.4 Output schemas and drift

`[REAL, measured]` §7.3 called a server 50 times for delivered orders:

| Server | Unvalidated client wrongly denied | Validating client flagged off-schema |
|---|---|---|
| v1 (`status`) | 0/50 | 0/50 |
| v2 (`state`) | **50/50** | **50/50** |

Nothing in the unvalidated path raised an exception: `dict.get("status")` returns `None`, `None != "delivered"`,
and the refund logic did what it was written to do with the data it was given. **Output validation converts a
logic error with no stack trace into a schema error with a precise path.**

Where validation fails, the client should not guess. Surface it as a tool failure, log the server name, version
(from `serverInfo`) and the schema path, and — in an agent — tell the model the tool is currently unavailable
rather than passing on a malformed object.

### 5.5 Servers validate their own output

The server side of the same contract is a MUST: if a tool declares `outputSchema`, its `structuredContent` must
conform. `[REAL, measured]` §7.4 built results from v2's drifted object: without a self-check the result shipped
with `isError: false`; with a self-check it became an explicit `isError: true` failure. A server-side check in
tests (or in production, for high-stakes tools) catches drift **before** any client sees it.

For backward compatibility, a result carrying `structuredContent` should also carry the same JSON serialized in
a `TextContent` block, because older clients only read `content`:

```json
{"resultType":"complete",
 "content":[{"type":"text","text":"{\"order_id\":\"O-1001\",\"status\":\"delivered\",\"amount\":40.0}"}],
 "structuredContent":{"order_id":"O-1001","status":"delivered","amount":40.0},
 "isError":false}
```

### 5.6 `$ref` and the network

`[REAL, measured]` §7.5: a local `$ref` to `#/$defs/money` resolved and rejected `-5`; a `$ref` to
`http://169.254.169.254/latest/meta-data/` was **refused** and the schema rejected.

The address is not arbitrary. `169.254.169.254` is the instance metadata endpoint on major clouds, which can
return credentials (M11-L05). A client that followed `$ref`s would let any server make the client issue requests
inside the client's network — **server-side request forgery** (SSRF, M9-L12). The spec's rules follow directly:
no network dereferencing by default; any opt-in mode must use a host allowlist or at least block loopback,
link-local and private addresses, with timeouts, size limits and logging; and a schema with an unresolved
external `$ref` SHOULD be rejected rather than treated as permissive.

### 5.7 Composition keywords and validation cost

`[REAL, measured]` §7.6 built schemas in which each level refers to the level below twice through `anyOf`:

| Depth | Schema size | Evaluations | With a 5,000-evaluation budget |
|---|---|---|---|
| 4 | 583 B | 122 | validated |
| 8 | 1,107 B | 2,042 | validated |
| 12 | 1,639 B | 32,762 | **rejected** |
| 14 | 1,907 B | 131,066 | **rejected** |

The schema grows by about 130 bytes per level; the work roughly quadruples every two levels. A hostile or careless
server can publish such a schema, and every client that validates arguments against it pays the cost on every call.
Bounds — maximum depth, maximum subschemas, or a time budget — convert that into a rejected tool definition.

### 5.8 Assumptions and limitations

- The lab's validator is a **teaching subset** (no `format`, `unevaluatedProperties`, `$dynamicRef`, or dialect
  switching). Use a complete, maintained validator in production and still apply §5.6–§5.7's limits around it.
- §7.1's corpus is hand-written to resemble common model errors; its counts illustrate *categories* of mistakes,
  not their frequency in any particular model.
- Schema *design for the model's benefit* — descriptions, examples and naming that raise first-attempt accuracy —
  is M9-L15.

## 6. Worked example — the refund tool that accepted a limit override

**The situation.** A support MCP server exposed `issue_refund(order_id, amount, reason)`. Its schema declared the
three properties and `required`, but not `additionalProperties: false`, ranges, or an enum for `reason`. The handler,
written in Python, took `**kwargs` so that an internal back-office caller could pass `override_limit=True` for
refunds above the normal £500 cap.

**The incident.** An agent handling an angry customer called:

```json
{"order_id":"O-4471","amount":1250,"reason":"goodwill","override_limit":true}
```

The refund went through. The conversation log showed the model had seen `override_limit` mentioned in an internal
runbook that had been retrieved into its context as a resource.

**Applying the lesson.**

1. **Which schema rules would have stopped it?** From §5.2's table: `additionalProperties: false` (the extra
   field), `maximum: 500` (the amount) and an `enum` for `reason` (`goodwill`). Any one of the three would have
   rejected this call; types alone would have accepted it.
2. **Why was the override reachable at all?** The handler read `**kwargs` — §5.3's future-facing risk realised. A
   capability intended for one trusted internal caller was exposed to every caller of the MCP tool.
3. **Would output validation have helped?** No — the result was well-formed. This was an input and authorization
   failure.

| # | Defect | Fix |
|---|---|---|
| 1 | Schema allowed undeclared properties | `additionalProperties: false` |
| 2 | No range or enum constraints | `maximum`, `minimum`, `enum` for `reason` |
| 3 | Privileged option reachable through the public tool | Separate internal API; never read undeclared kwargs in an MCP handler |
| 4 | Server relied on the schema alone | Server-side validation **and** an authorization check on refund size (M9-L13) |

**The general rule.** **An input schema is the narrowest description of what a caller may ask for. Anything it does
not forbid, assume a model will eventually send.**

## 8. Common mistakes and troubleshooting

1. **Treating the schema as documentation and not validating.** §5.2 — a type-only check missed half the flawed
   payloads.
2. **Omitting `additionalProperties: false`**, especially on no-parameter tools. §5.3, §6.
3. **Reading undeclared keyword arguments in handlers.** §6 — makes hidden options model-reachable.
4. **Declaring `outputSchema` without checking conformance in the server's tests.** §5.5.
5. **Consuming `structuredContent` without validating it**, or accepting `.get()` → `None` silently. §5.4.
6. **Following remote `$ref`s**, or treating an unresolved `$ref` as "anything goes". §5.6.
7. **Validating server-supplied schemas with no depth or work limit.** §5.7.

| Symptom | Likely cause | Fix |
|---|---|---|
| Model's calls "work" but produce wrong business outcomes | Type-correct but out-of-range or invented values | Add `minimum`/`maximum`, `enum`, `pattern` |
| A no-argument tool behaves differently on some calls | Handler reads model-invented kwargs | Strict empty-object schema; ignore undeclared args |
| Downstream logic makes wrong decisions after a server upgrade | Output drift | Validate `structuredContent` against `outputSchema`; alert on failure |
| Client hangs or CPU spikes when listing one server's tools | Pathological composition schema | Bound validation depth/work; reject the tool |
| Unexpected outbound requests from the host | Validator dereferencing remote `$ref` | Disable network `$ref` resolution |

## 9. Security, privacy, reliability, cost

- **Security.** The input schema is the first control on what a model can ask a tool to do (§6); it is not the last
  — authorization still applies (M9-L13). Server-supplied schemas are untrusted input to clients (§5.6–§5.7).
- **Privacy.** A permissive schema can let a model pass fields such as `include_pii: true` that a handler happens to
  honour. Forbid what you don't declare.
- **Reliability.** Output validation is how you learn about a breaking server change from the first call rather
  than from a customer (§5.4).
- **Cost.** Client-side input validation prevents paid round trips that will fail anyway; bounded validation prevents
  a single schema from consuming CPU on every call.

## 12. Revision notes

- **Default dialect 2020-12.** `inputSchema` is required with root `type: "object"`; `outputSchema` is optional.
- **Validate fully.** Measured: required-only **2/12**, +types **6/12**, full schema **12/12**. The dangerous
  mistakes are type-correct.
- **No-parameter tools:** `{"type":"object","additionalProperties":false}` (strict accepted 1/5 vs loose 5/5).
- **Output drift is silent without validation** (50/50 wrong decisions, 0 errors). Servers MUST conform to
  `outputSchema`; clients SHOULD validate; also send a `TextContent` copy.
- **`$ref`:** never auto-dereference network URIs (SSRF); reject unresolved external refs.
- **Composition:** bound depth/work — a 1.6 kB schema demanded 32,762 evaluations.
