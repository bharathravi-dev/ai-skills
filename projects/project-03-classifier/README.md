## What this project is

A complete binary classifier — data, split, model, threshold, metrics, report — with **every step
implemented directly in NumPy** rather than delegated to scikit-learn. Roughly 700 lines of source and
600 lines of tests.

**The point is not the model.** It is a logistic regression on six features, and you could fit a better
one in four lines of scikit-learn. The point is that **every decision that determines whether the
reported number means anything is visible, deliberate, and tested.**

Most of the ways a machine-learning result goes wrong are not modelling errors. They are:

- a split that lets the model see the answer,
- a metric that measures the majority class,
- a threshold chosen on the data it is then evaluated on,
- a score reported with no baseline to compare it against,
- a gradient that is subtly wrong and never checked.

This project makes each of those **structurally hard to get wrong**, and the test suite fails if you do.

## The five things this project enforces

### 1. The gradient is verified before anything is believed

`model.py` derives the weighted cross-entropy gradient by hand. Section 2 of the report checks it
numerically against a central difference **on four different training subsets** before the pipeline
proceeds, and raises if the worst relative error exceeds 1e-7.

Four subsets rather than one, because [M3-L11 §7.3](../../modules/module-03-math-ml-essentials/M3-L11-backpropagation.md)
measured a real missing-ReLU-mask bug **passing** a gradient check run on a single convenient input.

`tests/test_model.py::test_a_broken_gradient_is_caught` deliberately halves the gradient and asserts
the check **fails** — a verification step that cannot fail is decorative.

### 2. No customer spans two parts of the split

`grouped_temporal_split` partitions customers first, then takes only the latest months for evaluation,
with a discarded gap month between. It calls `assert_no_group_leak` on its own output before returning,
so a leak raises at the point it is created rather than surfacing as a suspiciously good score.

### 3. The test set is read once, after every decision is made

Two tests enforce this by reading `train.run`'s own source:

- `test_no_test_labels_are_read_before_the_threshold_is_chosen` — every threshold decision must
  complete before the first `data.y[split.test]`.
- `test_the_test_set_is_scored_exactly_once` — exactly one `report(...)` call on test data.

A convention that is not enforced is a convention that will be broken.

### 4. No metric is reported without a baseline

Section 6 prints the model beside always-negative, always-positive and random-at-base-rate baselines.
The accuracy line prints the do-nothing baseline next to it, and the PR-AUC line prints the base rate,
because PR-AUC is uninterpretable without it.

### 5. The threshold is chosen from stated costs, on validation

`choose_threshold_by_cost` minimises `12·FP + 240·FN` on validation. Those costs are **assumptions
belonging to the business**, printed in the report and repeated in the limitations. No threshold
chooser in `evaluate.py` accepts a test set — `test_no_threshold_chooser_accepts_a_test_set` checks
their signatures.

## Reading the result

**The accuracy line is the one to look at first.** The model scores **0.6317** while the do-nothing
baseline scores **0.9392**. By accuracy, this model is far worse than predicting "nobody churns" — and
that is correct, expected, and exactly why accuracy is the wrong metric here. The model catches **64 of
73** churn events (recall 0.8767) at the cost of 433 false alarms, because the stated costs say a miss
is 20× worse than a false alarm.

**Precision 0.1288 against a base rate of 0.0608** means flagged customers are about **2.1× more likely
to churn** than a randomly chosen one, and **PR-AUC 0.3725 against a random baseline of 0.0608** is a
**6.1× lift**. Those are the numbers that describe whether the model is useful. Neither is impressive
in absolute terms, and both are honest.

**ECE 0.2765 is poor, and it is poor by construction.** Class weighting shifts predicted probabilities
away from observed frequencies — [M3-L14 §5.5](../../modules/module-03-math-ml-essentials/M3-L14-metrics.md).
The model ranks well (ROC-AUC 0.8384) and its probabilities should not be read as probabilities. This
is stated in the limitations rather than quietly omitted, and it is precisely the situation where an
expected-cost decision made from raw model output would be wrong.

**Section 7 contains a negative result, and it is the most instructive part of the project.**

| Setup | PR-AUC | ROC-AUC |
|---|---|---|
| Grouped + temporal, honest features | 0.3725 | 0.8384 |
| **(a)** Random split, honest features | 0.3495 (**−0.0230**) | 0.8390 |
| **(b)** Honest split, target-encoded feature | 0.4596 (**+0.0871**) | 0.9161 |

**(a) The random split did not leak.** Not because grouped splitting is unnecessary, but because this
feature set contains no customer identifier and the model is linear, so there is no mechanism by which
it could memorise an individual. [M3-L13 §7.3](../../modules/module-03-math-ml-essentials/M3-L13-splits-imbalance.md)
measured a **16.7-percentage-point** gap on the same kind of data *with* an identity feature. Add a
customer embedding, an ID column or a high-capacity model, and the leak appears at once.

**(b) One feature leaked badly on a perfectly correct split.**
`customer_churn_rate_alltime` is each customer's mean label across every month, so each row's feature
already contains its own answer. PR-AUC rises 23% and ROC-AUC by 0.078. **The split was right and the
result is still worthless.**

Together these say something more useful than either alone: **the rule is not "always group your
split". The rule is: find the mechanism by which information travels from the answer to the features,
and close it.** Sometimes that is the split. Here it was a feature no split could have saved. A rule
applied without its mechanism is superstition.

## Security, privacy and cost notes

- **All data is synthetic**, generated deterministically from a seed. No real, employer, customer or
  learner data is used or required anywhere in this project.
- **No credentials of any kind.** `test_no_secrets_or_credentials_in_the_package` asserts that no
  module mentions `api_key`, `secret`, `password` or `aws_access`.
- **Nothing is provisioned and nothing is billable.** The project runs on a laptop CPU in seconds.
- **`customer_churn_rate_alltime` is a deliberate anti-pattern**, present only so its effect can be
  measured. It is opt-in (`add_leaky_feature=True`), documented as leaky in its own docstring, and
  never used by the default pipeline.
- **Grouping by a customer identifier is a privacy consideration in real work.** You need the grouping,
  not the identity — hash or pseudonymise the key, and never let a raw identifier into a shared
  artefact.
- **The slice report is a demonstration of technique, not a fairness assessment**, and no metric in
  this project establishes legal compliance with anything. M10 covers what governance actually
  requires.
